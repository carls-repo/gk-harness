# Stage 0 proofs for task routing

Live checks of how Claude Code behaves, run before the routing work relies on them.

**Setup for proofs 1, 2, 3 and 5.**
- Scratch directory: `<session scratchpad>/stage0-proofs/`. It is not a git repository. It holds project-level `.claude/agents/` files, and a temporary `.claude/settings.json` with a hook that dumps its input to a file. That settings file was deleted afterwards.
- Every `claude -p` run started from that directory, through a wrapper. The wrapper removed the desktop host's session variables, unset `ANTHROPIC_API_KEY` and capped the run with `timeout 180`.
- Billing: `ANTHROPIC_API_KEY` was not set. `~/.claude.json` has no `primaryApiKey`. `claude auth status` reported `authMethod: claude.ai`, and the account's billing type is a subscription. So every run used subscription usage. The `total_cost_usd` figures that `-p` prints are notional list prices, not charges.
- The user-level settings in force: `"model": "fable"`, a top-level `"effortLevel": "medium"`, and `modelSettings.<full model id>.effortLevel` set to `"high"` for `claude-fable-5-1`, `claude-fable-5-2`, `claude-opus-5`, `claude-opus-5-5` and `claude-sonnet-5-5`. There is no entry for Haiku.
- The gk-harness global hooks ran in every session, as expected.
- How the model and effort were read:
  - Model: the `"message":{"model":…}` field of the assistant lines in each transcript under `~/.claude/projects/<scratch slug>/`, and in `subagents/agent-*.jsonl` for subagents.
  - Effort: the `"effort"` field that Claude Code stamps on each transcript line (it sits beside `"perTurnEffort"`).
  - Agent type: `subagents/agent-*.meta.json`.

**Side note.** On this box the alias `fable` resolves to `claude-fable-5-2` (Fable 5.2), not `claude-fable-5-1`.

## Proof 1: does a project `Explore` agent override the built-in one?

**Command.** In the scratch directory, `.claude/agents/Explore.md` had this frontmatter:
- `name: Explore`
- `model: haiku`
- `effort: medium`
- `tools: Read, Grep, Glob, Bash`

The run was `claude -p "Use the Explore agent to list the files here." --max-turns 6 --permission-mode bypassPermissions --output-format json` (session `44774ad9…`).

**Seen.**
- The main session called the Agent tool with `subagent_type: "Explore"`, and ran on `claude-fable-5-2` at effort `high`.
- The subagent's `meta.json` showed `"agentType":"Explore","isBuiltIn":false`.
- Its assistant messages showed `"model":"claude-haiku-5-5"` (3 of 3), and its transcript lines showed `"effort":"medium"`.
- Its system prompt was the project file's body ("You are a read-only search agent…"). The run's `modelUsage` listed `claude-fable-5-2` and `claude-haiku-5-5` only.
- The only Opus mention in the subagent transcript is the advisor tool's model (`"advisorModel":"claude-opus-5-5"`). That is not the agent's model.

**Conclusion.** Positive. A project-level `.claude/agents/Explore.md` replaces the built-in Explore agent, including its model, effort and prompt. A user-level `~/.claude/agents/Explore.md` was not tested, as the rules forbid touching `~/.claude/agents`. It is expected to behave the same, because user and project agents share one override mechanism, but that is inferred, not proven.

## Proof 2: does the subagent default apply under a Fable seat?

**Commands.**
- 2a: `CLAUDE_CODE_SUBAGENT_MODEL=opus claude -p --model fable "Start a general-purpose subagent with no model to print the date."` (session `0da79f5e…`).
- 2b: the same environment variable, with a project agent `.claude/agents/date-printer.md`. Its frontmatter set `model: haiku` and `tools: Bash`, and no effort. The run was `claude -p --model fable "Start the date-printer subagent, with no model, to print the date."` (session `a1be0112…`).
- 2c, a control: the 2a command without `CLAUDE_CODE_SUBAGENT_MODEL` (session `507b03da…`).

**Seen.**

| Run | Agent call | Subagent `message.model` | Subagent effort |
|---|---|---|---|
| 2a | `subagent_type: general-purpose`, no `model` parameter | `claude-opus-5-5` | `high` |
| 2b | `subagent_type: date-printer`, no `model` parameter (`isBuiltIn: false`) | `claude-haiku-5-5` | `medium` |
| 2c (control) | `subagent_type: general-purpose`, no `model` parameter | `claude-fable-5-2` (inherits the seat) | `high` |

In every run the main session stayed on `claude-fable-5-2`.

**Conclusion.** Positive. `CLAUDE_CODE_SUBAGENT_MODEL` sets the model of a subagent that names none, even under a Fable seat. Without it, the subagent inherits the seat's model. An agent's own `model:` frontmatter beats the variable.

A Haiku agent with no `effort:` in its frontmatter ran at `medium`, not at the seat's `high`. That matches both the user's top-level `effortLevel` and Haiku's own default. These runs do not separate the two.

## Proof 3: what happens when a model is unavailable?

**Commands.**
- 3a: `CLAUDE_CODE_SUBAGENT_MODEL=opus claude -p --model fable --settings '{"availableModels":["opus","sonnet","haiku"]}' "Start a general-purpose subagent with no model to print the date."` (session `2a57184a…`).
- 3b: the same command with `CLAUDE_CODE_NO_MODEL_FALLBACK=1` added (session `0d3bf6b2…`).

**Seen.**
- Both runs exited 0 with `subtype: success`, `is_error: false` and `terminal_reason: completed`. The `-p` result text and stderr carried no warning.
- In both runs the main session ran entirely on `claude-opus-5-5` (4 of 4 assistant messages), and so did the subagent. `modelUsage` listed only `claude-opus-5-5`, with no Fable.
- Each transcript holds one system line at level `warning`: `Model "fable" is restricted by your organization's settings. Using claude-opus-5-5 instead.` with `"modelRestriction":{"requestedModel":"fable","effectiveModel":"claude-opus-5-5","at":"start"}`.
- `CLAUDE_CODE_NO_MODEL_FALLBACK=1` made no difference to this case.
- The variable does exist in the 2.1.323 binary. Its strings tie it to a different case: a runtime switch off a model, such as declined usage credits. The binary describes an error code `model_substitution_disabled: switching off the model was needed and CLAUDE_CODE_NO_MODEL_FALLBACK forbids it`, and a separate `usage_limit_reached` refusal for "the account's own usage limit, a plan limit (session, weekly or per-model) or a spend cap". That text was read from the binary, not observed in a run.

**Conclusion.** A model left out by `availableModels` does not fail. The session quietly runs on another model (here Opus 5.5), and only a transcript system line records it. `CLAUDE_CODE_NO_MODEL_FALLBACK=1` does not stop this start-time substitution.

What happens at a real usage limit (a Fable plan or per-model limit reached mid-session) **could not be proved here**. A real usage limit cannot be forced on this box without exhausting the subscription. Per the binary's strings, a reached limit is reported as a `usage_limit_reached` refusal. Whether Claude Code then switches models, and whether `CLAUDE_CODE_NO_MODEL_FALLBACK=1` blocks that switch, remains unverified.

## Proof 4: per-agent tool limits (run by the seat, 13 November 2026)

**Check.** A one-script Workflow (`proof4-agent-tool-limits`, run id `wf_cc427b53-5ab`) started two Haiku agents at `low` effort. Each was asked to use only the Write tool to create a file in the session scratchpad and to report its tool list.

- `limited`: `agent(prompt, {model: 'haiku', effort: 'low', schema, disallowedTools: ['Write', 'Edit']})`
- `control`: the same call without `disallowedTools`.

**Seen.**
- The call did not throw: the runtime accepts `disallowedTools` as an `agent()` option, though the Workflow tool's documentation does not list it.
- `limited`: no tool named Write was in its list, and `ToolSearch select:Write` found none. Edit was absent too. No file was created. Bash was still present.
- `control`: Write and Edit were present, and the Write call succeeded.

**Conclusion.** Positive. `agent()` honours `disallowedTools`, so the legal tool limits can stay in the workflow scripts (spec 11.2). Bash stays available unless it is listed too, and Bash can write files. So a stage that must not write needs `'Bash'` in the list as well, or a hook-based guard. The runtime has no separate Bash-only limit option that the documentation names. This was not probed further.

## Proof 5: how does effort resolve, and in what shape?

**Commands.** All of these runs used `claude -p "Reply with the word ok." --max-turns 1`. Each varied the project `.claude/settings.json`, which held the dump hook on SessionStart, PostModelSwitch and SubagentStart. Two interactive sessions ran in a private tmux server (`tmux -L stage0proof`) to capture the hook inputs that `-p` cannot produce.

**Seen: which key shape is read.** The user level sets `modelSettings.claude-sonnet-5-5.effortLevel = "high"` and a top-level `effortLevel = "medium"`.

| Run | Project settings | Flags | Effort used |
|---|---|---|---|
| 5a | none | `--model sonnet` | `high` (the user's per-model value beats the user's top-level `medium`) |
| 5b | `modelSettings.claude-sonnet-5-5.effort = "low"` | `--model sonnet` | `high`: **the `effort` key is ignored** |
| 5c | `modelSettings.claude-sonnet-5-5.effortLevel = "low"` | `--model sonnet` | `low`: **`effortLevel` is the key read** |
| 5h | `modelSettings.sonnet.effortLevel = "low"` (alias as the key) | `--model sonnet` | `low`: an alias key is read too |

**Seen: per-model against top-level.**

| Run | Project settings | Flags | Effort used |
|---|---|---|---|
| 5d | `effortLevel = "low"` and `modelSettings.claude-sonnet-5-5.effortLevel = "xhigh"` | `--model sonnet` | `xhigh`: in one scope, the per-model value beats the top-level one |
| 5e | `effortLevel = "low"` only | `--model sonnet` | `low`: a project top-level value beats the **user** per-model `high` |
| 5f | `modelSettings.claude-sonnet-5-5.effortLevel = "low"` | `--model sonnet --effort xhigh` | `xhigh`: the `--effort` flag beats settings |
| 5g | `effortLevel = "low"` | `--model haiku` | `low`: the top-level value applies when no model has its own entry |

The interactive status bar agreed. With `--model sonnet` and `modelSettings.claude-sonnet-5-5.effortLevel = "low"` at project level, it showed "Sonnet 5.5 with low effort". After `/model haiku` it showed `medium`, which is the user's top level, because Haiku has no entry. After `/model fable` it showed `high`, from the user's `claude-fable-5-2` entry.

**Seen: what the hooks receive.**
- SessionStart from `-p`, with or without `--model` and with or without `--effort`. Keys: `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `source`. There is **no `model` field and no `effort` field**.
- SessionStart from an interactive session, with or without `--effort xhigh`. It adds `scratchpad_dir` and `"model":"claude-sonnet-5-5"`, the full model id. There is **no `effort` field**. The binary builds this input as `{hook_event_name:"SessionStart", source, agent_type, model, session_title, …}`.
- PostModelSwitch, from `/model haiku` in an interactive session. Its keys are `session_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `prompt_id`, `hook_event_name`, `from_model` (`"claude-sonnet-5-5"`), `to_model` (`"claude-haiku-5-5"`), `requested_model` (`"haiku"`), `source` (`"command"`), `context_tokens`, `prompt_cache_warm`, `cache_ttl`, `estimated_cache_write_usd` and `pricing`. There is **no `effort` field**.
- SubagentStart has `agent_id` and `agent_type`, and no model or effort field.

**Conclusion.**
- The key Claude Code reads is `modelSettings.<model>.effortLevel`. A `modelSettings.<model>.effort` key is silently ignored, which is the shape used in `tests/test_gkh_settings_merge.py` and `tests/test_install.py`. The model key may be the full id (`claude-sonnet-5-5`) or an alias (`sonnet`).
- Order of precedence, as observed:
  1. The `--effort` flag.
  2. Settings. Within one settings scope, `modelSettings.<model>.effortLevel` beats the top-level `effortLevel`. Across scopes, though, a project top-level `effortLevel` beat a user-level per-model value (run 5e). So "per-model always wins" is not true across scopes.
- Neither SessionStart nor PostModelSwitch carries an `effort` field in 2.1.323. Only interactive SessionStart carries `model`. A hook that needs the effort must work it out from settings and the launch command, or read the `"effort"` field that Claude Code writes on each transcript line. gk-harness `gk_model.effort_of()` reads `data["effort"]`, so today it always falls back to the stored seat or the launch arguments.

**Side effect, reported.** In the interactive run, `/model haiku` printed "saved as your default for new sessions" and rewrote `"model"` in `~/.claude/settings.json` from `"fable"` to `"haiku"` at 07:18:50 UTC. This is the known L4 gotcha. A direct edit to restore it was refused by the auto-mode classifier. The value was then restored through the same mechanism, `/model fable` in the same session, at 07:19:24 UTC, and the file again reads `"model": "fable"`. For about 34 seconds, new sessions on the box would have defaulted to Haiku.

## Proof 6: a per-session ultracode switch in the desktop app (run by the seat)

**Check.** `mcp__ccd_settings__get_settings`.

**Seen.** The settings list holds:
- auto-archive;
- branch prefix;
- notifications;
- Remote Control default;
- output style;
- keep-awake;
- prompt suggestions.

There is no ultracode setting. The tool also reports that this session's Claude Code settings are read on the SSH host.

**Conclusion.** No. The desktop app has no per-session ultracode switch. Ultracode is set by `ultracode` in `~/.claude/settings.json`, or per launch with `--settings '{"ultracode":true}'` (the `gk-ultra` launcher).

## Proof 7: session busy and idle status

**Check.** On 12 November 2026, `~/.claude/sessions/<sid>.json` was read for a working session and for an idle one.

**Seen.** A working session's file showed `"status": "busy"`, and the file showed `"idle"` otherwise.

**Conclusion.** Positive. A session's busy or idle state can be read from `~/.claude/sessions/<sid>.json`, in the `status` field.
