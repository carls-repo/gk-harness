# gk-harness

A portable installer that puts Claude Code hooks, worker agents, workflows and a policy file into any machine's `~/.claude`. Requires Python 3.9 or newer (standard library only).

## Install

macOS / Linux:

```sh
git clone git@github.com:carls-repo/gk-harness.git ~/.gk-harness && ~/.gk-harness/install.sh
```

Windows PowerShell:

```powershell
git clone git@github.com:carls-repo/gk-harness.git $HOME\.gk-harness; powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\.gk-harness\install.ps1"
```

Run it again at any time: an install that finds nothing to change writes nothing.

## What the installer changes

| Target | Source | Rule |
|---|---|---|
| `~/.claude/hooks/gk-harness/*.py` | `hooks/*.py` | copied |
| `~/.claude/hooks/gk-harness/routes.json` | `routes.json` | copied; the hooks read the seat facts and tiers from it |
| `~/.claude/agents/worker-*.md`, `~/.claude/agents/Explore.md` | `agents/` (generated from `routes.json`) | copied; an existing file of the same name is backed up first |
| `~/.claude/workflows/gk-*.js` | `workflows/` | copied, with the same backup rule |
| `~/.claude/CLAUDE.md` | `policy.md` | the marker block. Its first line inside is `<!-- generated by gk-harness: edit policy.md in the gk-harness repo, then run install -->`. If the file has no block and its first line is `# Model orchestration policy`, the whole file is the old policy: back it up and replace it with the block alone (otherwise there would be two live policies). If not, keep the content and append the block |
| `~/.claude/settings.json` | registrations below, and four owned keys | merged; see "Settings the installer owns" |
| `~/.claude/gk-harness.json` | this checkout | `{version, root, python, installed_at}`; the SessionStart hook reads `root` for its once-a-day update check |
| shell rc | `shell/aliases.*` | a block between `# >>> gk-harness >>>` and `# <<< gk-harness <<<` that exports `GK_HARNESS_ROOT` (this checkout) and sources `<root>/shell/aliases.sh`, or sets `$env:GK_HARNESS_ROOT` and runs `. "<root>/shell/aliases.ps1"` on Windows |

Anything outside the `CLAUDE.md` block is this machine's own notes and is kept. In `settings.json` the installer owns the hook entries whose command runs a script under `hooks/gk-harness/`, and the four keys below. It never touches the top-level `effortLevel`, `permissions`, `autoMode` or any other entry.

### Settings the installer owns

The values come from `routes.json` `seat`:

| Key | Value | Why |
|---|---|---|
| `model` | `"opus"` | new sessions, desktop-app ones included, start on the default seat |
| `modelSettings.<model id>.effortLevel` | the seat effort for Opus, Fable and Sonnet (`medium`) | each seat model starts at its routed effort |
| `env.CLAUDE_CODE_SUBAGENT_MODEL` | `"opus"` | a subagent with no model of its own runs on Opus, not on a Fable seat |
| `ultracode` | `false` | ultracode is per session, through `gk-ultra` |

The first install adopts each key: it writes the value and records what was there before (or that nothing was), so `uninstall` can put it back. After that, the installer writes a key only while it still holds the value the installer last wrote, as the journal records it. A key you change or remove by hand after that, for example with `/model`, is left alone: `install` and `update` do not overwrite it, `status` lists it as hand-changed, and `uninstall` leaves it as you set it. To hand a key back to the installer, set it to the value in the table, then run `install`.

`status` also warns when `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` or `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL` is set, in `settings.json` `env` or in the environment: either one overrides every agent's own model, so the routing would not hold.

The shell rc file is:

- macOS: `~/.zshrc`;
- Linux: `~/.zshrc` if `$SHELL` ends in `zsh`, else `~/.bashrc`;
- Windows: the `$PROFILE` that `pwsh` (else `powershell`) reports. If neither answers, the installer says so and skips this step.

An rc file, `CLAUDE.md` or `settings.json` that is a symlink (as stow or home-manager make them) is edited where it points, and stays a link. An rc file that cannot be written, such as a link into a read-only store, is skipped with a notice, as one that cannot be read is. On Windows an empty profile (as `New-Item $PROFILE -Force` leaves it) gets a UTF-8 byte-order mark, as a new one does, so that Windows PowerShell 5.1 reads the block as UTF-8; `uninstall` returns it to empty.

### Launchers

The rc block sets `GK_HARNESS_ROOT` to this checkout and defines four shell functions:

| Name | Runs |
|---|---|
| `gk` | `claude --model opus --effort medium`: the default seat |
| `gk-fable` | `claude --model fable --effort medium`; `/effort high` gives a hard turn more |
| `gk-ultra` | `gk` with ultracode on for the session, for audits and broad sweeps |
| `gkh` | `python3 "$GK_HARNESS_ROOT/install.py"` (`python` in PowerShell): the installer's commands, below |

`gk-opus` and `gk-sonnet` are retired, and a new shell no longer defines them. The launchers are shortcuts only, and nothing depends on them. A desktop-app session starts on the saved `model` (`opus`), and uses the `#deep` dial per turn where `gk-ultra` would turn ultracode on.

On Windows the installer never changes PowerShell's execution policy. The `gk`, `gk-fable`, `gk-ultra` and `gkh` functions load from your profile only when PowerShell may run profile scripts; if a new PowerShell window does not know them, run:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

### Hook registrations

Each command is `"<python>" "<claude_dir>/hooks/gk-harness/<script>"`, where `<python>` is the Python that ran the installer (re-run `install` after a Python upgrade), with `timeout: 10`.

| Event | Matcher | Scripts (in order) |
|---|---|---|
| SessionStart | — | `gk-seat.py`, `gk-peers.py` |
| PostModelSwitch | — | `gk-seat.py` |
| UserPromptSubmit | — | `gk-peers.py` |
| PreToolUse | `Workflow` | `gk-profile.py` |
| PostToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit` | `gk-claim.py`, `gk-remote-pending.py` |
| PostToolUse | `mcp__.*__(batch\|update\|create)\|Artifact\|SendUserFile` | `gk-remote-clear.py` |
| Stop | — | `gk-remote-stop.py` |
| SessionEnd | — | `gk-claims-end.py` |

### Backups and the journal

Every file the installer replaces is copied first to `~/.claude/backups/gk-harness/<UTC yyyymmddTHHMMSSZ>/`. Every change is recorded in the action journal `~/.claude/backups/gk-harness/manifest.json`, so that `uninstall` can reverse it. Each change is recorded before it is made, so an install cut short (a closed terminal, a crash, a power cut) is finished by running `install` again, or undone by `uninstall`.

Before its first write, `install` checks that Python is 3.9 or newer, that every source file is present, that `settings.json` is strict JSON (or absent), that no path it quotes holds `"`, `$` or `` ` ``, and that every file it would write (other than the shell rc file) can be written. If a check fails it exits with `gk-harness: <problem>; nothing was changed.`

### Pre-harness files

On a machine that ran the earlier `gk-*` hooks, `install` removes their `settings.json` entries and the old `alias gk…=` lines from the shell rc file, and records each removal. It leaves the old files where they are, because sessions started before the install may still call them. Once those sessions have ended, move the old files into the backup folder with:

```sh
~/.gk-harness/install.sh --retire-legacy
```

Windows PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\.gk-harness\install.ps1" --retire-legacy
```

## Uninstall

```sh
~/.gk-harness/install.sh uninstall
```

Windows PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\.gk-harness\install.ps1" uninstall
```

`uninstall` replays the journal in reverse. A file that is exactly as the installer left it gets its earlier state back. A file changed since is reversed surgically: in `settings.json` the installer's entries go and the removed entries come back; from `CLAUDE.md` and the shell rc file only the block is removed; a copied hook, agent or workflow you edited stays where it is, with the warning `changed since install, left in place: <path>`. Before it rewrites or removes a file you have edited since install, `uninstall` copies it to `~/.claude/backups/gk-harness/<UTC yyyymmddTHHMMSSZ>-uninstall/`, and names that folder at the end. A file that already matches its backup is left as it is. An uninstall cut short is finished by running it again. The backups stay.

## Update and status

```sh
~/.gk-harness/install.sh update    # git pull --ff-only, then install
~/.gk-harness/install.sh status    # version, root, python, owned entries, hand-changed keys and drift
```

`install` and `update` refuse, with exit code 3, while another Claude session on this machine is busy, so an update never swaps hooks under a working session. The message names the busy sessions. `update` checks before it pulls. Wait until they are idle and run it again, or pass `--ignore-busy`.

Windows PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\.gk-harness\install.ps1" update
powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\.gk-harness\install.ps1" status
```

`status` lists as drift every installed file that differs from this checkout or is missing, a policy block that `install` would change, and each hook entry `install` registers that `settings.json` lacks (all of them when the file is absent or unreadable). When none is lacking, it lists hook entries that `install` would still change.

## The `gkh` command

`gkh` runs `install.py` from this checkout, so every command works from any folder in a new shell:

| Command | What it does |
|---|---|
| `gkh install [--ignore-busy] [--retire-legacy]` | install, as above |
| `gkh update [--ignore-busy] [--retire-legacy]` | `git pull --ff-only`, then install |
| `gkh uninstall` | replay the journal in reverse |
| `gkh status` | version, root, python, owned entries, hand-changed keys, drift, and a warning for a variable that forces every agent's model |
| `gkh gen [--check]` | write every file generated from `routes.json`: the agents, each workflow's routes block and its phase labels, and the class table in `policy.md`. `--check` writes nothing, lists the stale files and exits 1 when there are any |
| `gkh report [--since YYYY-MM-DD] [--session ID] [--config-dir DIR] [--json]` | price the session, subagent and workflow transcripts from the `routes.json` prices, by session, day, workflow, stage, agent and model, with Fable's share and Haiku calls over the 100K-token prompt. Cost per class comes from the seat's `Route:` lines and is best effort. It reads only; on a subscription, cost is a proxy for your share of the usage limits |
| `gkh fable off`, `gkh fable on`, `gkh fable status` | the Fable switch, below |

Without `gkh`, run the same commands as `~/.gk-harness/install.sh <command>`, or `install.ps1 <command>` on Windows.

## Routing, dials and the Fable switch

`routes.json` is the one source for which model and effort does each kind of work. `gkh gen` writes the worker agents, each gk workflow's routes block and the class table in `policy.md` from it, and `gkh gen --check` fails when one of them is stale. Edit `routes.json`, run `gkh gen`, then `gkh install`.

A dial is a whole word at the start or end of a prompt. The seat passes it to gk workflows as a bare word, without the `#`, for example `args.dials: ['nofable']` (a workflow also strips one leading `#`):

| Dial | Effect |
|---|---|
| `#nofable` | no Fable stage or worker this turn; each Fable stage runs on its `noFable` tier |
| `#fable` | every apex stage (judge, plan check, adjudication, critic) runs on `fable-high` |
| `#deep` | run the matching gk workflow even where the seat would work solo |
| `#solo` | no workers or workflows this turn |

`gkh fable off` keeps Fable out until `gkh fable on`, for a usage limit that lasts hours or days. It writes `~/.claude/state/gk-fable-off.json`. While the file is there, the Workflow hook adds `nofable` to every gk workflow's dials and the seat card says "Fable is off". `gkh fable status` says which.

## After the update from v1

v2.0.0 replaces the three-seat policy with the routing policy, retires the profiles, and adds the four owned settings keys. The first update from v1 runs v1's `update`, which pulls before any busy check, then starts the new `install`. That install refuses while a peer session is busy, which leaves the checkout on v2 but not installed. In that half-installed state, new shells already get the v2 launchers while the v1 hooks stay live. Run `~/.gk-harness/install.sh install` once the peers are idle; `gkh` works in a new shell after that install succeeds. On Windows, `gk-ultra` also needs `GK_HARNESS_ROOT` to find its settings file, and only the v2 profile block sets it: in the half-installed state `gk-ultra` fails, so open a new shell after `install.sh install` (`install.ps1 install`) succeeds. Then run `status`: it should show no drift, and the four keys owned.

## Rollback

The tag `pre-routing` marks the last v1 commit. To go back to it, run the steps below while no peer session is busy. `uninstall` removes the hooks that running sessions call, so a peer's tool calls fail until the `install` in step 3 puts hooks back. `uninstall` does not check for busy peers itself, so look first: a session is busy while its `~/.claude/sessions/<id>.json` says `"status": "busy"`.

1. `~/.gk-harness/install.sh uninstall`
2. `git -C ~/.gk-harness switch --detach pre-routing`
3. `~/.gk-harness/install.sh install`

To return to the routing harness: `git -C ~/.gk-harness switch main`, then `~/.gk-harness/install.sh install`.
